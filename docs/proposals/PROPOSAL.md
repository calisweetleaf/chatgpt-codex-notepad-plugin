# PROPOSAL.md
## Conversation-Bound Cognitive Workspace (CBCW)
**Status:** Independent architecture proposal — v0.1  
**Author:** GPT-6, for comparative design review  
**Date:** 2026-10-31  
**Position:** Build a conversation-native, event-sourced working notebook exposed through a small MCP tool surface. Do **not** build another generalized memory system.

---

## 1. Thesis

A long-running ChatGPT conversation should behave like a persistent research environment, not a disposable sequence of prompts. Its assistant needs an **external working notebook** that preserves operational state across context compaction, model changes, and long gaps between sessions.

That notebook is not a second transcript, a user biography, an imitation chain of thought, or an automatic summarizer. It is a **conversation-scoped record of working commitments**: what we established, what we challenged, which premises failed, what remains open, how competing architectures diverged, and which evidence or artifacts support each claim.

My proposal is **CBCW: Conversation-Bound Cognitive Workspace**. Its central invariant is:

> **A conversation owns a workspace; a workspace owns a durable, inspectable sequence of research-state changes. No other conversation inherits that workspace by accident.**

This is the design I would build. I reject both a single global notepad and a conventional “vectorize everything and hope retrieval finds it” system.

## 2. Problem definition

There are three distinct problems, and confusing them will produce the wrong product.

1. **Context eviction:** The active model loses operational distinctions as a long conversation is compressed or truncated.
2. **Continuity reconstruction:** On returning, it must rebuild a working state from partial summaries instead of opening a current ledger.
3. **Conversation identity:** Standard tool access does not guarantee that the model is supplied with the native ChatGPT conversation title or ID. A plugin cannot assume access to either.

The first two are storage and retrieval problems. The third is a **binding problem**. An MCP server is not automatically omniscient about the chat that invoked it; it knows only the metadata and explicit tool arguments it receives.

The workspace must therefore be independently identified, and its binding to a particular conversation must be treated as a first-class protocol—not guessed from the latest user activity, date, topic, or title.

## 3. Non-goals

CBCW will **not**:

- request or reproduce private chain-of-thought or hidden reasoning traces;
- replace ChatGPT's existing memory, project context, or conversation history;
- scrape entire chats without an authorized host integration;
- record every message or promote every conversational aside into canon;
- infer that Aeron's ASPS, its model-facing memory heads, and a ChatGPT MCP notebook are the same architecture;
- silently merge research states from different chats;
- invent automatic hooks or native conversation metadata that the host has not actually exposed.

The target is an **assistant-operated research journal**, not a new artificial cognitive architecture for the underlying model.

## 4. The design I am asserting

### A. Workspace = conversation; corpus = optional federation

The primary namespace is an opaque `workspace_id` generated by the service. Every journal operation targets exactly one workspace. The backend may additionally support `project_id`, `topic_id`, or `branch_id`, but these are **links**, not permission to merge workspaces.

A conversation about Aeron should retain its own premises and decisions even if another chat discusses Aeron differently. The difference is research material, not noise to be smoothed away.

Cross-chat synthesis is a separate, explicit operation that produces a **new synthesis artifact** with references back to originating workspaces. It never rewrites source histories.

### B. Event-sourced journal, not mutable summaries

Each note is an append-only event with a stable ID, server timestamp, author, kind, scope, links, evidence, and revision lineage.

First-class kinds:

| Event kind | Meaning |
|---|---|
| `observation` | Something directly established by supplied material or tool output |
| `hypothesis` | A plausible but unproven working interpretation |
| `proposal` | A design the assistant or user affirmatively advances |
| `decision` | A direction explicitly adopted in the conversation |
| `constraint` | A boundary that future work must preserve |
| `correction` | An earlier statement was wrong, incomplete, or misattributed |
| `rejection` | A design or premise was considered and declined |
| `open_question` | An unresolved issue with a reason it matters |
| `experiment` | A proposed, executed, or observed test with its status |
| `artifact` | A pointer to a file, repository revision, document, or result |
| `checkpoint` | A derived snapshot of current state, linked to its source events |

A `correction` **supersedes** prior material; it does not delete it. A `rejection` must explain what was rejected, by whom, and on which evidence. A `proposal` remains visible as a real position even when subsequently displaced.

**Why append-only?** Because in research, the trajectory of revisions matters. If we erase the losing branch, we erase evidence about why we took the winning one.

### C. Two layers of recall

CBCW serves two distinct retrieval modes:

1. **Resume view:** A compact, deterministic working-state index: adopted decisions, active constraints, unresolved questions, recently changed assumptions, and next actions. This is the default on reattachment.
2. **Evidence view:** Query individual events, linked excerpts, revisions, branches, and artifacts by ID, keyword, semantic relevance, and temporal range.

The resume view is a **materialized projection**, never the source of truth. If it is wrong, it can be rebuilt from immutable journal events.

I would make full-text and structured retrieval work **before** adding embeddings. Semantic retrieval is useful, but a precise correction such as “ASPS is not an internal scratchpad file” must remain retrievable by exact name, relation, and event lineage—not only by similarity.

### D. The assistant writes; deterministic machinery organizes

The assistant decides **what is significant enough to record** and expresses it in ordinary operational notes. The service assigns IDs, timestamps, schema validation, deduplication hints, backlinks, version ordering, and projection updates.

The system should not try to manufacture notes by reconstructing hidden reasoning. Nor should it rely exclusively on an LLM periodically writing a beautiful but lossy summary.

Concretely, the assistant writes at **state transitions**, not after every turn:

- a decision becomes binding;
- a distinction or correction changes the model of the system;
- a competing branch is opened or closed;
- an experiment changes the evidence;
- a substantial topic is suspended;
- an explicit checkpoint is requested.

Tool invocations still require the host/model to invoke them. A server alone cannot force a write on every message or detect context compaction without supported host signals.

## 5. Conversation binding: the critical dependency

**This is the central engineering risk, and my proposal does not pretend it away.**

I favor this priority order:

**Tier 1 — Verified host conversation identity.** If a supported host extension/tool context exposes a stable, scoped conversation identifier, bind that identifier to a generated workspace ID on the server. Verify its lifecycle and security properties in a real ChatGPT test. Do not assume it exists.

**Tier 2 — Plugin-mediated launch and binding.** If a supported plugin/extension entrypoint can establish a workspace and reliably inject its reference into a newly started conversation's model-visible context, use it. Verify that the reference survives subsequent tool calls and practical compaction. Merely opening a new chat is **not**, by itself, reliable binding.

**Tier 3 — Explicit workspace anchor.** Until Tier 1 or 2 is proven, create a workspace with `workspace.create`, emit a short visible anchor (e.g. `CBCW: w_7e...`) in the initial conversation, and attach via `workspace.attach` when needed. An authenticated user can select the correct workspace from the plugin's UI if the model loses the anchor.

**Hard rule:** When the binding is unavailable or ambiguous, stop workspace-specific writes and request explicit reattachment. Never auto-select “most recent workspace,” “same topic,” or a guessed chat title.

A workspace ID is a locator, **not an authorization secret**. Authentication and workspace access checks are independent. Without a reliable native conversation ID, the service cannot cryptographically prove that two tool calls came from the same ChatGPT thread; the fallback must not claim that guarantee.

## 6. Minimal MCP surface

I would ship a small, boring API rather than 30 overlapping tools:

| Tool | Contract |
|---|---|
| `workspace.create` | Create and return workspace ID, metadata, and anchor |
| `workspace.attach` | Authenticate and explicitly select an existing workspace |
| `workspace.status` | Return binding status, latest revision, event counts, and active branches |
| `journal.append` | Append one or a batch of typed events, with idempotency keys |
| `journal.query` | Query exact IDs, filters, time windows, text, or semantic matches |
| `journal.revise` | Append a superseding correction or status change; never edit history silently |
| `workspace.checkpoint` | Materialize a sourced resume view at a chosen revision |
| `workspace.resume` | Fetch current resume view plus recent changes since last checkpoint |
| `branch.manage` | Open/close/link hypotheses and competing design branches |
| `workspace.compare` | Produce a cross-workspace *read-only* comparison when explicitly authorized |
| `workspace.promote` | Create an attributed project-level synthesis entry without deleting local provenance |

A concrete event envelope:

```json
{
  "workspace_id": "w_7e2f...",
  "event_id": "evt_01...",
  "kind": "correction",
  "subject": "Aeron/ASPS relationship",
  "statement": "Aeron's ASPS is a specialized one-to-one subsystem; do not collapse it into a generic internal scratchpad file.",
  "status": "active",
  "supersedes": ["evt_prior"],
  "source": {
    "type": "conversation",
    "locator": "user-supplied statement",
    "evidence_excerpt": "Aeron gets a specialized 1for1 system"
  },
  "authored_by": "assistant",
  "recorded_at": "server_assigned",
  "idempotency_key": "client_generated_unique_key"
}
```

This is illustrative, not a claim that ChatGPT supplies native message IDs or precise locators. If a source locator is unavailable, store that fact instead of inventing one.

## 7. Persistence and retrieval substrate

**Initial implementation:** A remote HTTPS MCP service with an authenticated SQLite-backed append-only event ledger, FTS5 search, and derived projection tables. SQLite is deliberate: one operator, low maintenance, strong transactions, simple backups, transparent export, and enough capacity for an extensive per-conversation research journal.

Logical storage:

```text
accounts/
  workspaces/
    metadata
    events               # immutable journal
    event_links          # supersession, evidence, dependencies
    branches             # competing lines of inquiry
    projections          # rebuildable resume state
    artifacts            # links and hashes, not automatic file ingestion
    access_audit
```

The diagram describes logical organization, **not** a requirement for one physical folder per event.

**Adab-Nebulae should be an adapter, not an initial dependency.** CBCW can expose its journal to Adab-Nebulae's temporal and semantic systems once the identity, provenance, and revision semantics are stable. This gives the workspaces richer retrieval without letting an external memory fabric blur conversation ownership or dictate the schema.

Likewise, Aeron's ASPS is a separate, model-specific mechanism with its own training and inference responsibilities. CBCW may produce useful research artifacts *about* ASPS; it must not pretend to be a substitute for its internal head/runtime architecture.

**Hosting choice:** Cloud-hosted first for reliable access from mobile and multiple devices. A local backend can be a development replica or self-hosted deployment, but a service reachable only from one laptop is a poor default for an Android-centered, cross-session workflow. The deployment must provide durable storage, backups, authentication, and export; the mere fact that a website can host an MCP endpoint does not guarantee all four.

## 8. Write policy and lifecycle

A typical session should work this way:

```text
Start/reattach
  -> resolve workspace binding (or explicitly reattach)
  -> workspace.resume
  -> reason normally with the live chat
  -> journal.append at significant state transitions
  -> workspace.checkpoint at a natural milestone
  -> resume in that same conversation later
```

Every checkpoint should contain:

- active objective and why it matters;
- accepted decisions and invariants;
- competing proposals **with their strongest arguments intact**;
- corrections/supersessions since prior checkpoint;
- open questions, blockers, and proposed tests;
- links to original events and artifacts;
- revision number and checkpoint creation time.

I would cap default resume output by a token budget and offer selective expansion through query. **No checkpoint may silently convert a hypothesis into a decision.** Status changes require explicit events.

The assistant can add notes without asking for consent on every routine write *after* the user has deliberately enabled this workflow. The notebook is still inspectable, editable through revision events, and exportable by the user. Policy and authorization boundaries remain enforced by the connector and backend.

## 9. My positions against nearby alternatives

**Against one global notebook:** It invites cross-chat contamination and destroys the intellectual independence of parallel research threads. Keep local workspaces; federate only by explicit synthesis.

**Against chat-title-as-primary-key:** Titles are mutable, non-unique, and may be inaccessible. Use service-minted IDs and treat names as labels.

**Against “just summarize the transcript”:** A summary compresses prose. A research journal records state changes, status, provenance, and disagreements. It can summarize, but summaries are secondary projections.

**Against embeddings-first memory:** Semantic relevance alone cannot preserve strict negative constraints, exact corrections, authorship, or version lineage. Structured events and exact retrieval come first.

**Against automated speculative journaling:** The tool should record meaningful claims the assistant actually makes or the user actually establishes, with uncertainty labeled. It should not manufacture hidden internal deliberation.

**Against forced consensus:** A rejected proposal remains a real proposal. Later models need something precise to challenge, not a harmonized narrative that hides disagreement.

**Against attaching every note to user-global memory:** User memory has a different purpose and scope. This is a working notebook bound to a particular research conversation.

## 10. Security and failure semantics

- Every event is account-scoped and workspace-authorized; workspaces cannot be enumerated across accounts.
- Avoid placing auth tokens in conversation text; keep ID and credentials separate.
- Encrypt transport and backups; define retention and deletion controls.
- Append operations have idempotency keys so retries do not duplicate events.
- Apply optimistic revision checks to checkpoints and competing updates.
- Exports include raw events and projections in portable JSONL/Markdown.
- If a projection is inconsistent with event lineage, rebuild it and report the mismatch.
- If a workspace cannot be reliably identified, **fail closed for writes**.
- Do not promise zero contamination without a tested chat-identity mechanism; measure it.

The notebook must survive **assistant mistakes**, not just outages. A wrong event should be superseded with a correction and made discoverable, not silently overwritten.

## 11. Build sequence

**Milestone 0 — Identity spike.** Determine exactly what conversation-scoped data the installed ChatGPT plugin/extension runtime exposes in actual use. Test fresh chats, resumed chats, model changes, and post-compaction behavior. Document every unsupported assumption. This is a gating experiment.

**Milestone 1 — Standalone journal.** Implement authenticated `workspace.create/attach`, `journal.append/query/revise`, event lineage, SQLite persistence, migrations, and deterministic resume projection. Build CLI/API tests independently of ChatGPT.

**Milestone 2 — MCP integration.** Expose the small tool surface, create a short plugin skill specifying *when* to write and *when* to resume, and test it from separate ChatGPT conversations. Include an explicit user reattachment flow.

**Milestone 3 — Evaluation.** Run long multi-topic sessions; introduce conflicting statements and corrections; deliberately simulate losing the chat anchor; test dedupe, ordering, evidence links, and incorrect workspace selection. Rebuild projections from scratch and compare results.

**Milestone 4 — Federation.** Add optional explicit cross-workspace comparison and project-level promotion, with immutable source citations. Connect Adab-Nebulae's semantic and temporal retrieval as an adapter only after the core invariants pass.

## 12. Acceptance criteria

1. A workspace can be resumed after a long chat with **no invented decisions**.
2. Each accepted decision and correction has an inspectable origin or is explicitly labeled unsupported.
3. Two chats on the same topic can preserve contradictory hypotheses without accidental merger.
4. Losing the workspace anchor never causes a silent write into a guessed workspace.
5. Replaying the event log reproduces the same canonical checkpoint projection.
6. A model can retrieve a specific negative constraint by exact term and relation, not merely semantic similarity.
7. A user can inspect, export, and supersede any assistant-written note.
8. The system works from the intended mobile/desktop environment, not only a developer terminal.
9. Retrieval is bounded and selective; the notebook does not simply flood the context window.
10. Host identity support is **tested and documented**, not assumed.

## 13. Questions for competing proposals to attack

I am intentionally leaving these as contested design questions rather than diluting the proposal into compromise:

1. **Identity:** Can another design establish automatic, durable chat binding without requiring unavailable host metadata or silent guessing?
2. **Granularity:** Is event-level journaling sufficient for high-density architectural work, or does it need a richer graph of assertions and relations from day one?
3. **Write timing:** What is the best practical trigger strategy when the assistant cannot depend on an every-turn hook or a compaction notification?
4. **Retrieval:** When does an Adab-Nebulae semantic-temporal index outperform FTS-plus-relational lineage enough to justify becoming a core dependency?
5. **Evaluation:** How do we quantify operational continuity, not merely similarity between a checkpoint and the conversation transcript?
6. **Workspace federation:** What explicit promotion protocol preserves incompatible lines of inquiry while still allowing useful global synthesis?

## 14. Final architectural judgment

Build **a transactional, event-sourced, conversation-bound research journal with a compact resume projection and explicit evidence retrieval**. Make its identity protocol honest about ChatGPT's limits. Give the assistant the tools and behavioral instructions to maintain it, but do not promise invocations the host does not guarantee.

Do not scale it into a universal memory fabric first. Do not flatten disagreement into one evolving summary. Do not confuse the journal with Aeron's ASPS. Let Adab-Nebulae enrich it after its basic guarantees hold.

**The success condition is not that the assistant remembers everything. It is that, when the live context becomes unreliable, the assistant can reopen the correct workspace and recover exactly what was established, what remains contested, and why.**

That is the architecture I would defend against competing proposals.
